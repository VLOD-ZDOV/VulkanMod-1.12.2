## Что работает

Vulkan рисует непрозрачный мир (SOLID, CUTOUT_MIPPED, CUTOUT) в общий с OpenGL кадр,
глубина переносится аппаратным блитом, композит идёт до сущностей. TRANSLUCENT, сущности
и частицы остаются на ванильном OpenGL.

Готово в этой версии: поддержка Windows (Win32-хендлы вместо файловых дескрипторов),
мип-уровни атласа, depth blit, два кадра в полёте, indirect-отрисовка, GPU-таймеры,
ультра-логирование, экран настроек в стиле VulkanMod, игровые оптимизации
(дальность сущностей и блок-сущностей, анимации, лимит FPS в фоне), совместная
загрузка с OptiFine.

## Замеры (дальность 12, окно высокого разрешения, дискретная карта)

```
fence wait 0.18–0.50 ms | record 0.08–0.25 ms | submit+composite 0.06–0.08 ms | GPU 0.18–0.24 ms
600–1430 fps в окнах замера
```

**Главный вывод: отрисовка мира на видеокарте стоит ~0.2 мс из ~0.7 мс кадра.**
Кадр уходит не в наш рендер, а в игровую логику вокруг него. Поэтому пункты раздела B
роадмапа (early-Z, сортировка front-to-back) дадут доли процента, а не десятки, и подняты
наверх пункты G4 — свои аналоги оптимизаций OptiFine.

Для сравнения: OptiFine на той же машине даёт 800–900 fps против наших ~700. Разрыв
создаётся тем, что OptiFine делает меньше работы **до** отрисовки, а не быстрее рисует.

Зеркало геометрии на дальности 12: **4321 аллокация, 232 МиБ VRAM** плюс столько же
закреплённой системной памяти под staging-копии. Работает — то есть лимит драйвера на
тестовой машине заметно выше гарантированных спецификацией 4096 (реальное значение печатается в
ультра-лог). Это расточительность, а не блокер; см. A1.

## Рабочий процесс

```bash
cd VulkanMod112
JAVA_HOME=<путь к JDK 26> ./gradlew build       # Java 17 не годится, RetroFuturaGradle требует новее
JAVA_HOME=<путь к JDK 26> ./gradlew runClient   # dev-клиент, PRIME-переменные уже в build.gradle
```

Собранный jar кладётся в папку `mods` тестового инстанса лаунчера — файлы модов читаются
только при запуске, так что копировать можно и при открытом лаунчере.

Диагностика: включить **Ultra Logging** (Video Settings → VulkanMod112 → Advanced) или
`-Dvulkanmod112.ultraLog=true`, затем читать `logs/vulkanmod112-diagnostics.log`. Там версии,
список модов, драйвер, все активные пути кода, разбивка времени кадра и счётчики ресурсов —
этого достаточно, чтобы разобраться в проблеме, не расспрашивая пользователя.

**Правки в больших файлах делать точечными заменами.** `VkTerrainRenderer.java` — около
1900 строк; один раз замена по срезу между методами снесла половину файла. Резервная копия
исходников — sources-jar в `build/libs`, обновляется при каждой сборке.

## Известные грабли (уже стоили времени)

1. **Разные GPU у OpenGL и Vulkan** — самая коварная. Игра падает с SIGSEGV внутри драйвера,
   без crash-report, лог обрывается на первом кадре терраина. Причина: GL-контекст ушёл на
   Mesa, а Vulkan выбрал дискретную карту. Мод теперь сверяет UUID устройства обеих сторон
   и отказывается от интеропа с понятным сообщением. Лечится переменными окружения
   (см. README, раздел Troubleshooting).
2. **`VkMemoryDedicatedAllocateInfo` требует `GL_DEDICATED_MEMORY_OBJECT_EXT`** перед
   импортом в GL, иначе GL читает мусор. На маленьких изображениях случайно работает.
3. **Ориентация Y** — используется стандартный viewport с положительной высотой; матрицы из
   GL дают перевёрнутую по Vulkan-конвенции картинку, что ровно совпадает с ориентацией
   текстур GL. Из-за этого лицевые грани идут **по часовой стрелке**.
4. **Буферы, на которые ссылается кадр в полёте, нельзя удалять** — отложенное освобождение
   по номеру кадра в `VkChunkMirror`, иначе `VK_ERROR_DEVICE_LOST`.
5. **Win32-хендл не переходит во владение GL** при импорте (в отличие от файлового
   дескриптора) — его закрывает `Interop.closeHandle`.
6. **Мип-уровни атласа берутся из GL**, а не генерируются в Vulkan: Minecraft строит их
   поспрайтово, а генерация по склеенному атласу смешала бы соседние текстуры.
